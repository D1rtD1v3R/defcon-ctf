ANTI-CHEAT REMOVED_
// WIN PAGE FLOW :: BEFORE & AFTER //
The DEFCON 2026 CTF originally gated leaderboard submission on a per-path localStorage stage-key check. The win page would look for b_s1..b_s4 (or i_s1..i_s4 / e_s1..e_s5) and refuse to render the submit form if any were missing. That made sense at first glance and broke at second glance — see why below.

THE PROBLEM

Two things were wrong with the original gate, and they compounded each other.

  • It didn't actually verify solving. Of the 13 stage-completion keys across the three paths, only 3 of them (one per path, on the final stage) were gated behind correct flag input. The other 10 were set automatically on page load. So the gate enforced "did you visit each URL", not "did you solve each puzzle". Anyone who knew the URL chain could pass it without solving a thing.
  • It broke the realistic player journey. The CTF lives on a physical floppy disk with a QR code. Players scan with a phone. Beginner is phone-friendly, but the intermediate and expert paths need a PC for binary decoding, XOR analysis, DevTools console inspection, etc. Crossing to a PC clears localStorage for the new origin/browser, so the gate would fail even for players who solved every puzzle legitimately.

PASTE-THE-FLAG VERIFICATION

The win page now hides everything sensitive (flag display, stats, time, leaderboard submit form) inside a display:none wrapper. A verify panel is visible by default. The celebration only reveals when the player proves they have the flag.

// BEFORE //

Win page renders the flag + stats + leaderboard form unconditionally. A script reads stage keys from localStorage. If any are missing, the submit form is replaced with a "NICE TRY" panel. The flag itself is still visible on the page.

// AFTER //

Win page renders only the verify panel by default. Celebration content is hidden. The flag value is not visible to anyone who didn't earn it. On valid flag (via URL hash or paste), celebration reveals.

TWO PATHS TO UNLOCK

The verify gate has two equally-valid unlock paths. Same-device players never see the verify panel; cross-device or direct-navigation players use the paste form.

// SAME-DEVICE FLOW //

1Player submits the correct flag on the final stage.
2Final stage stores ctf_elapsed and redirects to win.html#FLAG{…} with the flag in the URL hash.
3Win page's verify script reads location.hash, decodes it, compares to the hardcoded flag for that path.
4On match: celebration reveals. history.replaceState scrubs the hash from the address bar.

// CROSS-DEVICE / DIRECT-NAV FLOW //

1Player arrives at win.html with no hash (different device, cleared storage, or direct URL).
2Verify panel is the only thing visible. No flag, no leaderboard, no stats.
3Player pastes the captured flag into the input, clicks VERIFY (or hits Enter).
4On match: celebration reveals. On mismatch: inline error, celebration stays hidden.

WHO CAN DO WHAT, BEFORE vs AFTER

ScenarioOld gateNew gate
Same-device, normal solve Works Works (URL-hash auto-unlock, identical UX)
Phone-scan, PC-solve Breaks (gate fails on PC) Works (paste the captured flag)
Cleared storage / incognito after solving Breaks Works
Direct navigation to win.html Blocked (NICE TRY) Blocked (verify panel, no flag visible)
Player knows the URL chain (e.g., from writeup) but didn't solve Bypassed gate Still needs the flag
Player knows the flag itself Could already submit (set stage keys + submit) Could already submit (paste flag)
Random visitor sees the flag value on win.html Yes (flag displayed unconditionally) No (celebration hidden until verify)

The new gate is strictly stronger on the "did you solve it" axis, and strictly more forgiving on the "did you cross devices" axis. The only thing it gives up is the false certainty of the old design.

WHAT THIS CHANGED FOR ATTACKERS

  • No new exploitable surface introduced by the change.
  • The leaderboard remains the only piece of shared mutable state, and the worst-case impact of any practical attack still caps at a polluted leaderboard. Per-handle dedup exists; per-IP rate-limiting and a Worker-side minimum-elapsed check are recommended follow-ups.
  • The Cloudflare Worker's CORS policy (https://d1rtd1v3r.github.io only) is still doing its job — confirmed via direct OPTIONS probe.
